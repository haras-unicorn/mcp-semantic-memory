# Releasing

Releases are made by [release-plz](https://release-plz.dev) from the commit
history, which is why commits follow
[Conventional Commits](https://www.conventionalcommits.org). The workflows are
generated by the dev shell (`src/nix/dev/shell/default.nix`), so change them
there. The release-plz settings are in `release-plz.toml`.

The whole repository has one version, one tag (`v<version>`), one GitHub release
and one `CHANGELOG.md`. The crates share the version through a `version_group`,
and only the `-cli` package makes the tag and the release. Its changelog also
lists the changes of the library and store crates.

1. Every push to `main` runs the `release` workflow. Its `release-pr` step opens
   or updates a pull request that bumps the version and writes the changelog
   from the commits since the last release.
2. Merging that pull request, and only that, makes the `release` step publish
   every crate to crates.io, tag the commit `v<version>` and create the GitHub
   release. `release_always = false` in `release-plz.toml` is what stops other
   merges from releasing. release-plz knows a release pull request by its branch
   name, which starts with `release-plz-`, so do not rename those branches. A
   change that has to release without a bump of its own, like a CI fix, needs a
   branch with that prefix.
3. A published release runs the `build` workflow, which builds the static binary
   with Nix on x86_64 and aarch64 Linux and uploads it to that release as
   `mcp-semantic-memory-<system>`.

The `-testing` crate is not published. The core crate, the three store crates
and the `-cli` crate are. A crate that is added later has to be added to
`release-plz.toml` with the same `version_group`, or it gets a version and tag
of its own.

## Documentation

Every push to `main` runs the `docs` workflow, which builds the book with Nix
and deploys it to GitHub Pages.

## Before the first release

- Add two secrets to the repository: `RELEASE_PLZ_TOKEN`, a personal access
  token, and `CARGO_REGISTRY_TOKEN`. Tags and releases made with the default
  `GITHUB_TOKEN` do not trigger the `build` workflow, which is why the first one
  is needed.
- In the repository settings, set the Pages source to GitHub Actions.
- Let the release pull request bump the version, because it also writes the
  changelog. A published version can be yanked but never deleted.
- The five crate names were free on crates.io when this was checked
  (2026-11-10).
- Publish order matters to crates.io, because the stores depend on the core
  crate. release-plz works that out.
- The workflows were generated and have not been run yet. Expect to fix small
  things on the first run.

## Checks on every change

The `check` workflow runs on pull requests, and not on pushes to `main`, so
merging only goes through a change that was checked. It runs `nix flake check`.
That runs every dev shell check, builds the package and checks that the binary
is static. The container tests for Postgres and MariaDB run in the `test` check,
in a podman daemon inside the Nix build sandbox. That needs the `uid-range`
feature on the runner, which the generated workflow sets up. `dev check` does
the same from the dev shell.
